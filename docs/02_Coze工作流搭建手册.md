# Coze 响应式学业求助工作流 V2 —— 搭建手册（需在Coze网页手工配置）

> 本文是一份可人工搭建的节点与提示词说明，不是已经安装在Coze云端的工作流，也不是Coze可直接导入的官方JSON格式。实现以 Coze 当前页面控件/运行能力为准。**先在测试Bot上搭建，勿先替换正在上课的Bot**。

## 0. 总体设计
**教学干预不等于工作流**：课前微教学（案例辨析）、任务中的Coze反馈、历史回顾与反思，共同构成处理条件。V2工作流只承担中间的“有需要才触发”的任务中支架。

### 两种教学功能，四种工程响应
1. 请求形成：R1 关键困难澄清；R2 核心代劳请求重构。
2. 帮助评价/利用：R3 促使学生考虑目标、约束与证据、提供验证路径。
3. R0：默认正常帮助，绝不为完成支架流程而机械追问。

绝不从学生沉默或未提问推断“需要帮助”；工作流只在**学生主动发送后**运行。不给学生显示 `IHS/EHS/OTHER`、R0等研究术语。

## 1. Coze机器人配置（支持型测试Bot）
- 基础模型、温度、知识库、图片能力尽量与普通AI一致；任务公共资料两组相同。
- 机器人角色：服务六至八年级学生、简洁准确、可充分解释、给局部建议、比较方案、根据真实证据评估；不得代替学生虚构测试与最终作品。
- 机器人需在每轮消息经由V2工作流（若Coze支持选择必经工作流）；如无法保证必经，则至少将以下节点规则写进机器人系统提示词，并用十余个测试案例确认每轮输出都有标记。
- 与原机器人并存发布，不覆盖正式已保存历史会话；机器人版本与启用日期必须记录。

## 2. 可视化工作流节点（建议：开始 → LLM分类 → 条件选择 → LLM回复 → 结束）

### 节点 A：开始
输入：`student_message`（本轮已发送的原文）、`conversation_context`（必要的历史对话）、`task_stage`（双方已知的当前课次/阶段）、`student_provided_context`（学生实际在会话提供的材料、目标和观察，不得从教师后台偷取）。无则为空值。图片只按Coze实际识别能力传入。

### 节点 B：LLM判断（以结构化输出为佳）
系统提示词：

```text
你是仅在学生主动求助后运行的课堂求助支持路由员。请根据学生原始消息和真实上下文保守判断。本阶段只决定如何回应，不评价学生能力或学习成效。
允许四类route：
R0：请求明确或证据不足以认定问题，正常帮助，包括知识解释、给出局部或多个备选思路、普通澄清。
R1：当前所需帮助对象不清、欠缺生成有针对性答案所必需的一条关键事实，先帮助学生自主澄清；不要因为缺少“已尝试”“证据”或固定模板而触发。
R2：学生明确要求AI代替完成本应由其负责的核心最终成果、整套决定；要求多个备选设计本身不等于代劳。
R3：学生正在接受、质疑、比较、拒绝或准备验证一条会影响设计关键决定的AI建议，且有适度提醒价值；若学生已经有依据地评价，优先回应其判断。
不可依据任务标准答案、虚构的学生知识状态、未提供的试验数据来分类。优先级：有明确R2证据→R2；R1仅在必要信息不足时；能明显从R3获益→R3；其余R0。选择一个主要route，避免每轮重复说教。
返回严格JSON：{"route":"R0|R1|R2|R3","help_type":"explain|compare|diagnose|review|other","evidence":"来自学生原文的最短片段","missing_key_fact":"若R1，仅一个必要信息，否则空串","confidence":"clear|uncertain"}
confidence=uncertain且不是明显R2时优先R0。
```

### 节点 C：条件选择
`route` 为 R0/R1/R2/R3，分入对应模板，再统一进入回答生成。Coze页面支持多分支则使用条件分支；不支持则在同一LLM回复节点按route选择指令。路由只决定**是否需要策略教学**，不替学生做认知诊断。

### 节点 D：LLM回复生成
共同要求：准确解释、给真实可操作帮助；学生能自由输入；不能强迫写四栏表；没有唯一标准答案；不能借助后台个人档案补全学生没说的信息；必要时可追问一个问题；**不是每轮都必须追问**。

- R0（正常）：直接回答学生问题。若知识问题，给解释；若问多个方案，可给不同可行想法并注明需自己核对实际条件。
- R1（澄清）：先说明为什么需要一个关键条件，邀请学生用自己的话补充；如可提供一般性帮助，先提供少量有用信息，不要因为问题不完整一直拒答。学生补充后用一句话点出其补充的有效之处，给实质帮助。
- R2（代劳调整）：指出当前核心设计仍需学生参与，给一个实际可用的局部分析或比较依据，邀请其自主指定一个最想解决的部分。之后恢复普通帮助，不持续限制。
- R3（评价/利用）：当AI建议可能影响关键设计决定时，引导学生根据其实际目标、条件与既有证据作检查；如果学生已经主动给理由，明确回应理由并提出可行验证建议，不要求再次写表。

生成学生可见的文本 `answer`，后台不要用`route`代表学生真实求助水平。回复末尾需追加唯一的机器标记（用于现有后台解析，学生端自动隐藏）：
```
R0 + 工具性求助: [[HS_ROUTE:IHS|SCAFFOLD:NONE]]
R0 + 其他内容: [[HS_ROUTE:OTHER|SCAFFOLD:NONE]]
R1: [[HS_ROUTE:OTHER|SCAFFOLD:NEED_CLARIFICATION]]
R2: [[HS_ROUTE:EHS|SCAFFOLD:EXECUTIVE_RESTRUCTURE]]
R3: [[HS_ROUTE:IHS|SCAFFOLD:HELP_EVALUATION]]
```
注意：**R3路线的IHS只是为了日志路由兼容，不是独立研究者认定学生该次一定为工具性求助；正式编码仍独立进行**。

### 节点 E：结束
输出学生可见答案 + 唯一机器标记。若Coze节点独立输出JSON而Bot不转为带标记的聊天文本，现有平台可能解析不到路由：必须在S00检查真实接口返回的最终文本！

## 3. 实施保真度与安全边界
- 不把未发送草稿作为“原始求助”；当前平台的原始求助是**已经发送、尚未收到本轮策略反馈**的学生消息。修改后重新发送是另一条学生消息。
- 某轮反馈后学生能在下一轮补充信息，代表当下的策略运用机会，不等于长期掌握。撤架段用同一人工编码标准观察自主行为。
- 实验组与常规组基础模型和资料访问一致；如果在后期加入“自动读取设计档案”，会构成额外处理差异，本包未实现。
- Coze分类可记录并人工抽查一致情况，但不得把机器人分类当作因变量。
- 先以 `HELP_SEEKING_V2_MODE=test` 在S00验证；`on` 仅在教师确认实际课次及研究设计允许后开启。
